# Architecture and handover

How the Stone listing feed is put together, where each piece lives, and what a
new developer needs in order to take it over.

Last updated: 28 August 2026.

---

## 1. Read this first: the data is fabricated

The 500 listings currently in the database are **synthetic**. They were
generated by `scripts/generate-dev-fixtures.mjs`, not fetched from anywhere.

- Suburbs and postcodes are real Australian ones, so filtering behaves
  realistically
- Every property, address, price, agent, phone number and photo is **invented**
- Photos point at `picsum.photos`, a placeholder image service
- Agent emails use `@stone.example` — a reserved domain that cannot receive mail
- Every fixture file opens with a `_synthetic` banner saying so

The fixtures remain the default source, because they need no credentials and no
network. But they are no longer the only one: `AgentboxSource` has now run
against the live sandbox and its mapping is verified — see §2.

## 2. The sync is manual, not scheduled

```
Agentbox  ──▶  npm run db:seed:agentbox  ──▶  D1 database  ──▶  the app
(the CRM)         (run by hand)
```

The pull works. What does not exist is anything that runs it on its own:

- no scheduled job
- no webhook
- no polling
- nothing calling Agentbox at request time

The data sits in D1 and stays exactly as it is until someone runs the seed
again. That is the remaining gap — a cron trigger calling `fetchSince()` is the
shape of the answer, and `fetchSince` is written and tested.

### What has been built

`src/lib/ingestion/source.ts` defines a `ListingSource` interface with
`fetchAll`, `fetchSince` and `fetchOne`. Two implementations exist:

| File | State |
|---|---|
| `mock-source.ts` | In use. Reads the fixture files |
| `agentbox-client.ts` | **Sound.** Auth headers, pagination, retry, filters — all from the published API reference, all unit-tested |
| `agentbox-mapping.ts` | **Guesswork.** See below |
| `agentbox-source.ts` | Written and tested against a fake fetch. Never run against the live API |

`createListingSource()` in `src/lib/ingestion/index.ts` returns `MockSource`
unless Agentbox is explicitly switched on with credentials. Nothing else
changes when it flips, because nothing outside that folder imports a concrete
source.

### What the reference does not tell you

The published Reapit Sales API reference documents the listing response as an
empty object — `{ "listings": [ {} ] }` — so the mapping was originally
inferred from the filter vocabulary. Probing the sandbox replaced that guesswork
with fact, and turned up three things worth knowing before touching this code:

**1. Every request needs a `version` query parameter.** Omit it and the API
answers HTTP 300 "Invalid Version", naming versions 1 and 2. `AgentboxClient`
sends `version=2` on every call. This is not in the auth documentation, and it
fails before authentication is even considered.

**2. `/listings` does not return photos.** `include=images` is accepted there
and silently ignored — no error, no images. Photos exist only on
`/listings/{id}`. A complete sync is therefore a list walk plus one detail fetch
per listing, which is what `hydrate` does and why a full sync costs roughly one
request per listing rather than one per hundred.

The two endpoints take different includes, and the difference is easy to miss:

| Endpoint | Include | Returns |
|---|---|---|
| `/listings` | `relatedStaffMembers,mainDescription` | no photos, no `searchPrice` |
| `/listings/{id}` | `images,relatedStaffMembers,mainDescription` | everything |

**3. Most of an instance is not publishable.** On the sandbox, 1,167 of 2,103
listings carry `marketingStatus: "Not Listed"` — the appraisal and pre-listing
pipeline, internal CRM state with no business on a public site. The source
filters server-side to `Available, Sold, Leased, Under Contract`, leaving 936.

A fourth, smaller trap: rentals carry `searchPrice: "0"` and put the real figure
in `searchWeeklyRent`. Reading the wrong field prices every rental at zero while
everything else still looks correct.

### The API key is IP-allowlisted, and this shapes the sync

Reapit binds the API key to a set of source IP addresses. From an address that
is not on the list, every request returns:

```
401  {"errors":[{"code":"401","title":"Access Denied",
      "detail":"The IP is not allowed for the provided API key:<your ip>"}]}
```

Note this is **not** a bad-credentials error, and reads as one. If the key
suddenly stops working, check the egress IP before suspecting the key.

**This rules out running the sync from the Worker.** Webflow Cloud runs on
Cloudflare's edge, where outbound requests leave from a large and shifting pool
of IPs that cannot be enumerated, let alone allowlisted. So the obvious design —
a Cron Trigger in the Worker calling `fetchSince()` — cannot work against an
IP-bound key.

The sync has to run somewhere with a stable egress address and push into D1:

| Option | Notes |
|---|---|
| A small VM or container on a fixed IP | Simplest. Runs the existing seed script on a timer, `--remote` |
| GitHub Actions via a self-hosted runner or a NAT gateway | Hosted runners have dynamic IPs, so plain `ubuntu-latest` will not do |
| Ask Reapit to widen the allowlist | Only viable if they will accept a CIDR range; Cloudflare's is very large |

Whichever is chosen, the writing end is already built — `scripts/seed-d1.ts
--agentbox --remote` writes to the deployed database through wrangler.

To re-confirm any of this against a live instance:

```sh
npm run agentbox:probe          # needs .dev.vars with the credentials
```

It fetches one listing, prints the raw payload, lists the keys the mapping
ignores, and lists the `Listing` fields the mapping could not fill.

### Reference data comes free, but it is thin

Agentbox embeds the whole staff record inside every listing, under
`relatedStaffMembers[].staffMember`. So draining the feed also produces enough
of an agent and office directory for every listing to join up. `AgentboxSource`
collects them as it goes and offers them through `ReferenceDataSource`; the
loader prefers those over the fixture files whenever the source has them.

**That is not enough for directory pages**, which is why `DirectorySource` and
the `/offices` and `/staff` calls behind it exist. Measured against the sandbox:

| | From the listing feed | From the endpoints |
|---|---|---|
| Offices | ID and name only | address, phone, email, website, lat/long, status |
| Staff | 59, name and contact | 108, plus role, job title, status, `webDisplay` |

`/staff/{id}` adds the biography and specialist areas, and is called only for
the staff the publication policy will actually show — 12 requests here rather
than 119.

Without that, every real listing would join to an agent row that does not exist
and the cards would render "Stone" with no phone number.

### Safety rail

The client ID is base64 of the Agentbox admin URL, and it is what selects the
instance. `AgentboxClient` decodes it and **refuses any ID that does not
resolve to a sandbox**, unless `allowProduction: true` is passed deliberately.
Pointing this at live data is a decision someone has to make on purpose.

## 3. Where everything lives

```
   WEBFLOW (design)          GITHUB (code)           WEBFLOW CLOUD (running app)
  ┌─────────────────┐      ┌──────────────┐         ┌────────────────────────┐
  │ Listing Card    │      │ Astro app    │         │ staging  → /staging    │
  │ Buy / Rent /    │─(1)─▶│ SQL schema   │──(2)──▶ │ production → /app      │
  │ Properties      │ read │ seed script  │  build  │                        │
  │ design tokens   │      │ workflow     │         │  each has its own:     │
  └─────────────────┘      └──────────────┘         │   • D1 database        │
                                                     │   • env variables      │
                                                     └────────────────────────┘
```

**(1)** happens manually, at development time. **(2)** happens on deploy.
**Nothing flows right-to-left.** The running app never calls Webflow.

### What is in Webflow

The **design**, and nothing else. No data, no code.

| Thing | Detail |
|---|---|
| Site | `Stone`, id `6a73c4d12df78ea4c276a06b` |
| `Listing Card` component | 14 props bound to elements — this is the contract the app renders against |
| Pages | Home, Properties, Buy, Rent — design references |
| Design tokens | `--_stone-tokens---*` colours and sizes, copied into the app's CSS |

Webflow pages and the Webflow Cloud app are **separate surfaces**. The Webflow
pages are marketing pages; the app at `/app` is a Cloudflare Worker. They share
a domain, not a codebase.

### What is in Webflow Cloud

The **running application** and the **database**.

Webflow Cloud runs the app as a Cloudflare Worker. Each *environment* binds one
GitHub branch to one mount path:

| Environment | Branch | Mount | URL |
|---|---|---|---|
| staging | `staging` | `/staging` | `stone-6adb3b.webflow.io/staging` |
| production | `main` | `/app` | `stone-6adb3b.webflow.io/app` |

**Each environment has its own database and its own variables.** Seeding
staging does nothing for production. A `SEED_TOKEN` set on one does not exist on
the other. This catches people out.

## 4. Where the database actually lives

**Cloudflare D1** — a SQLite database running on Cloudflare's edge.

You do not have a Cloudflare account for it, and you do not need one. Webflow
Cloud provisions it, owns the account relationship, and manages it on your
behalf. That is why:

- `wrangler.json` carries a placeholder `database_id` (`123456789`). Webflow
  Cloud assigns the real one at deploy and overwrites it. **Do not go looking
  for a real ID — none exists to find.**
- Migrations in `migrations/` run **automatically on every deploy**
- The offline seed script cannot reach it — hence the seed endpoint

Locally, D1 is a SQLite file under `.wrangler/state/`, keyed by `database_id`.

### The tables

`listings`, `listing_images`, `listing_agents`, `offices`, `agents`,
`sync_runs`. Every identifier column is `TEXT`, never a number — listing IDs are
mostly 7 digits but some are 6, and a second identifier appears as `100P######`
or `IRE#######`. An integer column would corrupt all of those silently.

Deletes are soft: `deleted_at` and `last_seen_at`, never `DELETE FROM listings`.
Every row keeps its untouched source object in `raw_payload`, so a field needed
later can be re-derived locally rather than re-fetched.

## 5. DevLink — working, via OAuth

DevLink is Webflow's tool for exporting Webflow components into a codebase as
React. **It now runs.** `src/devlink/` is real export output, and
`listings.astro` renders the exported card.

Getting there took the third of three authentication routes:

| Route | Outcome |
|---|---|
| Site API token | Webflow removed per-site tokens from the UI entirely |
| Workspace API token | Generates, but the permission list has no DevLink Export row. Authenticates, then fails on the missing scope |
| **`npx webflow auth login`** | **Works.** The CLI's OAuth flow requests `devlink_export:read` directly, so it never depends on that dialog exposing a checkbox |

The OAuth session grants, among others, `devlink_export:read`,
`code_components:read` and `code_components:write`, and is stored outside the
repo at `%APPDATA%/webflow/auth.json`. It opens a browser and waits on a
localhost callback, so **it cannot run headless** — which is why the GitHub
Actions workflow, which expects a `WEBFLOW_API_TOKEN` secret, is still unusable.
Exports are a local command for now.

### The prop names are not ours

This is the thing to know before touching the call site. Webflow prefixes every
exported prop with the name of the **property group** it belongs to in the
Designer. A property called `suburb` inside a group called `Listing` arrives as
`listingSuburb`:

| Canonical `Listing` field | DevLink prop |
|---|---|
| `listingId` | `listingListingId` |
| `suburb` | `listingSuburb` |
| `displayAddress` | `listingDisplayAddress` |
| `priceDisplay` | `listingPriceDisplay` |
| `bedrooms` / `bathrooms` / `carspaces` | `listingBedrooms` / `listingBathrooms` / `listingCarspaces` |
| `photoCount` | `listingPhotoCount` |
| `agentName` / `agentPhone` | `agentAgentName` / `agentAgentPhone` |
| `contactUrl` | `agentContactUrl` — a `{ href, target?, preload? }` object, not a string |
| `hasOpenTimes` | `openHomeHasOpenTimes` |

Hard rule 3 in `CLAUDE.md` asks that Webflow property names match the canonical
field names, and they do — the prefixes are added by the exporter, not by
whoever named the properties. Renaming the groups in the Designer would remove
them, at the cost of losing the grouping that makes the component readable to
designers. The mapping is done once, at the call site in `listings.astro`, and
is commented there.

### Its CSS ships with it

`src/devlink/css/global.css` is a barrel that `@import`s the other five files
into named cascade layers. **Import the barrel, not the five.** Importing them
individually drops the `layer()` wrappers, and Webflow's resets then outrank the
app's own styles.

Class names are scoped to a generated wrapper — `DEVLINK_SCOPE_CLASS` in
`devlinkScope.ts` — so nothing leaks into the rest of the site.

### Still no image prop

The export confirms what was suspected: there is no prop for a photograph. The
card's media area is a `Block` (a plain `div`) with an empty `data-image`
attribute, and `listingPhotoCount` is a *number*, not a URL. Converting the
media area and the agent avatar to Image elements in the Designer and
re-exporting is what unblocks real photography — the URLs are already in D1.

`src/components/ListingCard.tsx` and `.css`, the hand-transcribed stand-in, are
now unused. They are kept for one release as a reference for diffing the
generated output against what was believed to be there.

## 6. Tooling — what runs, and where

| Tool | Where it runs | What for | Needed? |
|---|---|---|---|
| **Astro** | Build + server | The app framework | Yes |
| **wrangler** | Local only | Local D1, local preview | Local dev only |
| **webflow CLI** | Local / CI | The DevLink export | Only when the export works |
| **GitHub Actions** | GitHub | `DevLink export` workflow, manual trigger | Currently unused — blocked on the token |
| **Node test runner** | Local | `npm test`, 32 tests | Yes, built in — no test framework dependency |

No cron, no queues, no background jobs. The only scheduled thing that exists is
nothing — see §2.

### Commands

```sh
npm install
npm run fixtures     # regenerate synthetic data (deterministic)
npm run db:migrate   # apply migrations to local D1
npm run db:seed      # fill local D1
npm run agentbox:probe  # fetch one real listing and check the field mapping
npm run dev          # Astro dev server
npm run build        # production build
npm test             # unit tests
npm run typecheck
```

## 7. Deploying and seeding

1. Push to `staging` or `main`
2. Webflow Cloud builds that environment and runs the migrations
3. **The database will be empty** — migrations create tables, they do not load
   rows
4. Add `SEED_TOKEN` (type: Secret) to that environment's variables
5. Seed it, from the browser console on that site:

```js
await (await fetch('/staging/api/seed', {
  method: 'POST',
  headers: { 'content-type': 'application/json', 'x-seed-token': 'THE_TOKEN' }
})).json()
```

Use `/app/api/seed` for production. The `content-type: application/json` header
is required — Astro's CSRF protection rejects form-type POSTs with a 403 that
looks like an auth failure and is not one.

The endpoint is idempotent and fails closed: with no `SEED_TOKEN` configured it
returns 503 and refuses to run.

## 8. Taking this over without Claude

Honest assessment: **most of it is ordinary and any competent web developer can
maintain it.** Three things need explaining at handover.

### What is completely standard

Astro, TypeScript, SQLite/D1, plain SQL, GitHub Actions, a REST-ish endpoint.
No unusual dependencies, no framework nobody has heard of, no clever
abstractions. The query layer is one file of readable SQL. The tests use Node's
built-in runner.

Every non-obvious decision has a comment in the code explaining *why*, not just
what.

### The three things that need a person

**1. The card is generated, not exported.** Regenerating it means reading the
Webflow component and rewriting `src/components/ListingCard.*` by hand. A
developer can do this — the file header says exactly where it came from — but
the sustainable fix is getting DevLink working (§5), which makes it a CLI
command again.

**2. The sync runs by hand.** `AgentboxSource` is verified against the live
sandbox and `npm run db:seed:agentbox` fills the database from it, but nothing
runs on a schedule — the data is as fresh as the last time someone typed the
command. §2 says what the automated version looks like.

**3. Environments are independent.** Two databases, two variable sets. Seeding
or configuring one does nothing for the other.

### What a new developer should read, in order

1. `CLAUDE.md` — the rules and why they exist
2. This file
3. `src/lib/types/listing.ts` — the contract everything else agrees on
4. `src/lib/queries/listings.ts` — where the actual work happens
5. `README.md` — commands and the DevLink situation

### Known gaps

- No *scheduled* Agentbox sync. The client and mapping are verified against the
  sandbox and the pull works on demand; what is missing is a trigger that runs
  `fetchSince()` without a person (§2)
- `POST /api/seed` still loads the fixture JSON, not Agentbox. It is the only
  way to fill a deployed database (Webflow Cloud gives no CLI access to D1), so
  a deployed environment cannot yet be filled with real listings. Porting it is
  not a copy-paste: the endpoint runs under a 15-second budget and resumes via
  `?from=`, while a full Agentbox sync is ~940 requests
- The production Agentbox credentials have not been issued yet. Nothing in the
  code needs to change for them — `--allow-production` is the whole switch —
  but no run has ever addressed a live instance
- Offices carry only an ID and a name. The listing payload gives nothing more;
  filling suburb, phone and email needs a `/offices` sync that does not exist
- Detail pages at `/property/<slug>` exist and are server-rendered, but there
  is no Webflow component behind them: the Designer has a card and nothing
  else, so the markup is the app's own and will need re-doing against a
  `Listing Template` component when one is built. `/property/<listingId>`
  redirects to the current slug, so an address correction does not 404 an
  indexed URL
- The card has no image prop — **confirmed by the export**, not just suspected.
  The media area is a plain `div` with an empty `data-image` attribute.
  Converting it and the agent avatar to Image elements in the Designer, then
  re-exporting, is the only thing standing between the site and real
  photography: 1,356 image URLs are already in D1
- DevLink export runs locally but not in CI. The OAuth session cannot be
  obtained headless, and the GitHub Actions workflow still expects a
  `WEBFLOW_API_TOKEN` secret that no longer has a way to be issued
- The Webflow search panel and the Astro form are duplicate implementations and
  will drift. The Webflow one cannot submit: its Search control is a link, and
  all six inputs share `id="field"`
- Buy and Rent pages are set to publish with placeholder content
