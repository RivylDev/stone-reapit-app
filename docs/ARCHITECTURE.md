# Architecture and handover

How the Stone listing feed is put together, where each piece lives, and what a
new developer needs in order to take it over.

Last updated: 28 August 2026.

---

## 1. Read this first: the data is fabricated

The 500 listings currently in the database are **synthetic**. They were
generated by `scripts/generate-dev-fixtures.mjs`, not fetched from anywhere.

- Suburbs and postcodes are real Australian ones, so filtering behaves
  realistically
- Every property, address, price, agent, phone number and photo is **invented**
- Photos point at `picsum.photos`, a placeholder image service
- Agent emails use `@stone.example` — a reserved domain that cannot receive mail
- Every fixture file opens with a `_synthetic` banner saying so

**Nothing in this codebase has ever contacted Agentbox.** `CLAUDE.md` hard rule 2
forbids it, and that rule has been kept.

Before any real domain points at this, the fixtures must be replaced with a real
export. That is a file swap plus a re-seed — no code changes.

## 2. There is no sync yet

This is the most important gap to understand.

```
Agentbox  ──✗ nothing ✗──▶  D1 database  ──▶  the app
(the CRM)                    (500 fake rows)
```

The database was filled **once, by hand**, by POSTing to `/api/seed`. There is:

- no scheduled job
- no webhook
- no polling
- no connection of any kind to Agentbox

The data sits in D1 and stays exactly as it is until someone runs the seed
endpoint again. Building the real sync is unstarted work — see §8.

What *does* exist is the shape for it. `src/lib/ingestion/source.ts` defines a
`ListingSource` interface with `fetchAll`, `fetchSince` and `fetchOne`. The
current implementation, `MockSource`, reads the fixture files. A future
`AgentboxSource` implements the same three methods, and `createListingSource()`
in `src/lib/ingestion/index.ts` returns it instead. Nothing else changes,
because nothing outside that folder imports a concrete source.

## 3. Where everything lives

```
   WEBFLOW (design)          GITHUB (code)           WEBFLOW CLOUD (running app)
  ┌─────────────────┐      ┌──────────────┐         ┌────────────────────────┐
  │ Listing Card    │      │ Astro app    │         │ staging  → /staging    │
  │ Buy / Rent /    │─(1)─▶│ SQL schema   │──(2)──▶ │ production → /app      │
  │ Properties      │ read │ seed script  │  build  │                        │
  │ design tokens   │      │ workflow     │         │  each has its own:     │
  └─────────────────┘      └──────────────┘         │   • D1 database        │
                                                     │   • env variables      │
                                                     └────────────────────────┘
```

**(1)** happens manually, at development time. **(2)** happens on deploy.
**Nothing flows right-to-left.** The running app never calls Webflow.

### What is in Webflow

The **design**, and nothing else. No data, no code.

| Thing | Detail |
|---|---|
| Site | `Stone`, id `6a73c4d12df78ea4c276a06b` |
| `Listing Card` component | 14 props bound to elements — this is the contract the app renders against |
| Pages | Home, Properties, Buy, Rent — design references |
| Design tokens | `--_stone-tokens---*` colours and sizes, copied into the app's CSS |

Webflow pages and the Webflow Cloud app are **separate surfaces**. The Webflow
pages are marketing pages; the app at `/app` is a Cloudflare Worker. They share
a domain, not a codebase.

### What is in GitHub

All the code. `RivylDev/stone-reapit-app`.

| Path | Purpose |
|---|---|
| `src/lib/types/listing.ts` | The canonical `Listing` type — the contract |
| `src/lib/ingestion/` | `ListingSource` interface, `MockSource`, seed file reader |
| `src/lib/queries/listings.ts` | `search()` — every filter, sort and facet count |
| `src/lib/queries/params.ts` | URL parameter names and parsing |
| `src/pages/listings.astro` | The search page, server-rendered |
| `src/pages/api/seed.ts` | Protected endpoint that fills a deployed database |
| `src/components/ListingCard.*` | The card — **generated, see §5** |
| `migrations/` | SQL that creates the tables |
| `scripts/` | Fixture generator, offline seed loader, filter verifier |
| `seed-*.dev.json` | The synthetic data |
| `.github/workflows/` | The DevLink export workflow |

Branches: `main` (production), `staging`, and a working branch. `main` and
`staging` currently hold identical trees.

### What is in Webflow Cloud

The **running application** and the **database**.

Webflow Cloud runs the app as a Cloudflare Worker. Each *environment* binds one
GitHub branch to one mount path:

| Environment | Branch | Mount | URL |
|---|---|---|---|
| staging | `staging` | `/staging` | `stone-6adb3b.webflow.io/staging` |
| production | `main` | `/app` | `stone-6adb3b.webflow.io/app` |

**Each environment has its own database and its own variables.** Seeding
staging does nothing for production. A `SEED_TOKEN` set on one does not exist on
the other. This catches people out.

## 4. Where the database actually lives

**Cloudflare D1** — a SQLite database running on Cloudflare's edge.

You do not have a Cloudflare account for it, and you do not need one. Webflow
Cloud provisions it, owns the account relationship, and manages it on your
behalf. That is why:

- `wrangler.json` carries a placeholder `database_id` (`123456789`). Webflow
  Cloud assigns the real one at deploy and overwrites it. **Do not go looking
  for a real ID — none exists to find.**
- Migrations in `migrations/` run **automatically on every deploy**
- The offline seed script cannot reach it — hence the seed endpoint

Locally, D1 is a SQLite file under `.wrangler/state/`, keyed by `database_id`.

### The tables

`listings`, `listing_images`, `listing_agents`, `offices`, `agents`,
`sync_runs`. Every identifier column is `TEXT`, never a number — listing IDs are
mostly 7 digits but some are 6, and a second identifier appears as `100P######`
or `IRE#######`. An integer column would corrupt all of those silently.

Deletes are soft: `deleted_at` and `last_seen_at`, never `DELETE FROM listings`.
Every row keeps its untouched source object in `raw_payload`, so a field needed
later can be re-derived locally rather than re-fetched.

## 5. DevLink — configured, but not currently in use

DevLink is Webflow's tool for exporting Webflow components into a codebase as
React. **It is set up but has never successfully run.**

Authenticating it needs a token carrying the "Read DevLink Export data"
permission, and that has proved unobtainable for this workspace:

| Route | Outcome |
|---|---|
| Site API token | Webflow removed per-site tokens from the UI entirely |
| Workspace API token | Generates, but the permission list has no DevLink Export row. The token authenticates and then fails on the missing scope |
| `npx webflow auth login` | **Untried.** Worth a go: the CLI requests `devlink_export:read` itself rather than relying on that dialog |

**So `src/components/ListingCard.tsx` and `.css` are not DevLink output.** They
were written by reading the live Webflow component through the Webflow MCP — its
element tree, each class's real properties, and the site's design tokens — and
transcribing them. The result is accurate, and the prop names match the Webflow
component exactly, but:

> **It does not track design changes.** When someone edits the card in Webflow,
> nothing updates automatically. The files must be regenerated by hand.

If the export is ever made to work, it writes to `src/devlink/` and the swap is
one import line in `listings.astro`. The workflow and config are already in
place for that day.

## 6. Tooling — what runs, and where

| Tool | Where it runs | What for | Needed? |
|---|---|---|---|
| **Astro** | Build + server | The app framework | Yes |
| **wrangler** | Local only | Local D1, local preview | Local dev only |
| **webflow CLI** | Local / CI | The DevLink export | Only when the export works |
| **GitHub Actions** | GitHub | `DevLink export` workflow, manual trigger | Currently unused — blocked on the token |
| **Node test runner** | Local | `npm test`, 9 tests | Yes, built in — no test framework dependency |

No cron, no queues, no background jobs. The only scheduled thing that exists is
nothing — see §2.

### Commands

```sh
npm install
npm run fixtures     # regenerate synthetic data (deterministic)
npm run db:migrate   # apply migrations to local D1
npm run db:seed      # fill local D1
npm run dev          # Astro dev server
npm run build        # production build
npm test             # unit tests
npm run typecheck
```

## 7. Deploying and seeding

1. Push to `staging` or `main`
2. Webflow Cloud builds that environment and runs the migrations
3. **The database will be empty** — migrations create tables, they do not load
   rows
4. Add `SEED_TOKEN` (type: Secret) to that environment's variables
5. Seed it, from the browser console on that site:

```js
await (await fetch('/staging/api/seed', {
  method: 'POST',
  headers: { 'content-type': 'application/json', 'x-seed-token': 'THE_TOKEN' }
})).json()
```

Use `/app/api/seed` for production. The `content-type: application/json` header
is required — Astro's CSRF protection rejects form-type POSTs with a 403 that
looks like an auth failure and is not one.

The endpoint is idempotent and fails closed: with no `SEED_TOKEN` configured it
returns 503 and refuses to run.

## 8. Taking this over without Claude

Honest assessment: **most of it is ordinary and any competent web developer can
maintain it.** Three things need explaining at handover.

### What is completely standard

Astro, TypeScript, SQLite/D1, plain SQL, GitHub Actions, a REST-ish endpoint.
No unusual dependencies, no framework nobody has heard of, no clever
abstractions. The query layer is one file of readable SQL. The tests use Node's
built-in runner.

Every non-obvious decision has a comment in the code explaining *why*, not just
what.

### The three things that need a person

**1. The card is generated, not exported.** Regenerating it means reading the
Webflow component and rewriting `src/components/ListingCard.*` by hand. A
developer can do this — the file header says exactly where it came from — but
the sustainable fix is getting DevLink working (§5), which makes it a CLI
command again.

**2. The data is fake and there is no sync.** Someone must build
`AgentboxSource` against the `ListingSource` interface, and something must call
it on a schedule. Until then the listings are frozen fiction. This is the
largest piece of unbuilt work.

**3. Environments are independent.** Two databases, two variable sets. Seeding
or configuring one does nothing for the other.

### What a new developer should read, in order

1. `CLAUDE.md` — the rules and why they exist
2. This file
3. `src/lib/types/listing.ts` — the contract everything else agrees on
4. `src/lib/queries/listings.ts` — where the actual work happens
5. `README.md` — commands and the DevLink situation

### Known gaps

- No Agentbox sync (§2)
- Detail pages at `/listings/<slug>` do not exist and return 404
- The card has no image prop, because the Webflow component's media area and
  agent avatar are plain `div`s rather than Image elements. Converting them in
  the Designer unblocks real photos
- The Webflow search panel and the Astro form are duplicate implementations and
  will drift. The Webflow one cannot submit: its Search control is a link, and
  all six inputs share `id="field"`
- Buy and Rent pages are set to publish with placeholder content
